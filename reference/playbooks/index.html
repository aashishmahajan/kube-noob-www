Troubleshooting playbooks

67 offline playbooks. diagnose matches pasted events, describe output, logs or CLI errors against them and lists read-only steps before anything that changes the cluster. Try one in the playground.

Container keeps crashing (CrashLoopBackOff)

DBG-CRASHLOOP · kubernetes, openshift, rosa-classic, rosa-hcp · rules KN-C003, KN-C005

Likely causes

  • The process exits right after start (bad config, missing env/secret, failed migration, wrong command).
  • Liveness probe kills a slow-starting app (look for 'Liveness probe failed' before each restart).
  • OOMKilled at startup (see lastState.terminated.reason).
  • On OpenShift: the image expects root or a fixed UID and cannot write its directories under the random restricted-v2 UID.
  • CrashLoopBackOff is the waiting state between restarts, not a cause: the kubelet restarts the container with an exponential back-off (10s, 20s, 40s...) capped at 300 seconds, and resets it once the container has run for 10 minutes without a problem.
  • An init container fails (Init:CrashLoopBackOff): the app containers never start, and `logs --previous` without -c shows nothing useful.

Read-only checks

  • oc logs {pod} -n {ns} --previous # output of the crashed attempt
  • oc get pod {pod} -n {ns} -o jsonpath='{{.status.containerStatuses[*].lastState.terminated}}'
  • oc describe pod {pod} -n {ns} # Events: probe failures, OOMKilled, exit codes
  • oc get events -n {ns} --field-selector involvedObject.name={pod} --sort-by=.lastTimestamp
  • oc get pod {pod} -n {ns} -o jsonpath='{{.status.initContainerStatuses[*].lastState.terminated}}'
  • oc logs {pod} -n {ns} -c <init-container> --previous # the failing init container's own output

Image cannot be pulled (ImagePullBackOff / ErrImagePull)

DBG-IMAGEPULL · kubernetes, openshift, rosa-classic, rosa-hcp · rules KN-S012, KN-C013

Likely causes

  • Typo in image name or tag; tag was deleted or never pushed.
  • Private registry without an imagePullSecret linked to the pod's ServiceAccount.
  • Docker Hub anonymous rate limit (toomanyrequests).
  • Registry TLS not trusted by the nodes (x509) or the registry is unreachable from the node network (egress/proxy restrictions; on ROSA private clusters check NAT/VPC endpoints).
  • Architecture mismatch is a different error ('exec format error' after pull).
  • An image built only on your workstation (minikube, a local Docker) is in no registry, and a ':latest' tag or no tag makes imagePullPolicy default to Always, so the kubelet tries to pull it.

Read-only checks

  • oc describe pod {pod} -n {ns} # exact pull error in Events
  • oc get pod {pod} -n {ns} -o jsonpath='{{.spec.containers[*].image}}'
  • oc get sa {sa} -n {ns} -o jsonpath='{{.imagePullSecrets}}'
  • skopeo inspect docker://<image> # from a workstation with the same credentials
  • oc get deploy <deployment> -n {ns} -o jsonpath='{{.spec.template.spec.containers[*].image}} {{.spec.template.spec.imagePullSecrets}} {{.spec.template.spec.serviceAccountName}}' # image, pull secrets and ServiceAccount the pods get

Pull secret not found in the pod's namespace (FailedToRetrieveImagePullSecret)

DBG-PULLSECRET · kubernetes, openshift, rosa-classic, rosa-hcp · rules KN-C013

Likely causes

  • imagePullSecrets name Secrets in the pod's own namespace only (they are LocalObjectReferences): kubelet looks up {secret} in {ns}, and a Secret of that name in any other namespace is never used.
  • The Secret exists in the namespace under another name, or the pod's ServiceAccount links a name that is missing (the ServiceAccount's imagePullSecrets are also looked up in its own namespace).
  • [OCP] The image is in the internal registry of another project: no pull secret is needed, the pod's ServiceAccount needs the system:image-puller role in that project.

Read-only checks

  • oc describe pod {pod} -n {ns} # FailedToRetrieveImagePullSecret names the secret kubelet could not find
  • oc get pod {pod} -n {ns} -o jsonpath='{{.spec.imagePullSecrets}} {{.spec.serviceAccountName}}'
  • oc get sa {sa} -n {ns} -o jsonpath='{{.imagePullSecrets}}'
  • oc get secrets -n {ns} --field-selector type=kubernetes.io/dockerconfigjson -o name # names only
  • oc get secrets -A --field-selector metadata.name={secret} -o custom-columns=NAMESPACE:.metadata.namespace,NAME:.metadata.name # where it really is

Container killed for exceeding memory (OOMKilled / exit 137)

DBG-OOM · kubernetes, openshift, rosa-classic, rosa-hcp · rules KN-C004, KN-C005

Likely causes

  • Memory limit lower than the working set (JVM/Node heaps sized for the host, not the container).
  • Memory leak or unbounded cache.
  • Node-level OOM (OOMKilling event on the node) caused by pods without limits.

Read-only checks

  • oc describe pod {pod} -n {ns} # Last State: Terminated, Reason: OOMKilled
  • oc adm top pod {pod} -n {ns} --containers
  • oc get events -A --field-selector reason=OOMKilling

Container cannot be created (CreateContainerConfigError)

DBG-CONFIGERR · kubernetes, openshift, rosa-classic, rosa-hcp

Likely causes

  • Referenced Secret/ConfigMap or key does not exist in the pod's namespace.
  • runAsNonRoot conflict (see DBG-RUNASROOT).
  • Invalid volume subPath or mount of a missing key.

Read-only checks

  • oc describe pod {pod} -n {ns}
  • oc get secret,configmap -n {ns}
  • oc get pod {pod} -n {ns} -o jsonpath='{{.spec.containers[*].envFrom}}{{.spec.containers[*].env}}'

A string sent over gRPC is not valid UTF-8 (string field contains invalid UTF-8)

DBG-INVALID-UTF8 · kubernetes, openshift, rosa-classic, rosa-hcp

Likely causes

  • An environment variable from a Secret or ConfigMap (env valueFrom or envFrom) holds bytes that are not valid UTF-8, so the container runtime rejects the gRPC request (error unmarshalling request: string field contains invalid UTF-8) and the pod stays in CreateContainerError: typically a value base64-encoded twice under the Secret's data (Kubernetes decodes it once, leaving random bytes) or binary data such as a key or keystore.
  • Reported after node upgrades to containerd 2.2: pods using the same Secret failed on the new nodes and still started on nodes running containerd 2.1.
  • RHACS Collector in CrashLoopBackOff with String field 'storage.ProcessSignal.args' contains invalid UTF-8 data: a process on the host has arguments that are not UTF-8 (RHACS 4.5, tracked as ROX-26025; no workaround published).

Read-only checks

  • oc describe pod {pod} -n {ns}
  • oc get pod {pod} -n {ns} -o jsonpath='{{.spec.containers[*].envFrom}}{{.spec.containers[*].env}}'
  • oc get secret <secret> -n {ns} -o go-template='{{{{range $k, $v := .data}}}}{{{{$k}}}}{{{{"\n"}}}}{{{{end}}}}'
  • oc get nodes -o wide
  • oc get pods -n stackrox
  • oc logs <collector-pod> -c collector -n stackrox --previous

Pod refuses to start because the image runs as root

DBG-RUNASROOT · kubernetes, openshift, rosa-classic, rosa-hcp · rules KN-S003, KN-S004

Likely causes

  • runAsNonRoot: true but the image's USER is root (0) or a user name instead of a numeric UID.

Read-only checks

  • oc describe pod {pod} -n {ns}
  • skopeo inspect --config docker://<image> | jq .config.User

Pod rejected by SecurityContextConstraints

DBG-SCC · openshift, rosa-classic, rosa-hcp · rules KN-S001, KN-S004, KN-S009, KN-S010

Likely causes

  • The pod asks for something restricted-v2 forbids: fixed runAsUser/fsGroup outside the namespace range, privileged, hostPath, hostNetwork, added capabilities, allowPrivilegeEscalation: true.
  • The ServiceAccount was never granted the more permissive SCC the workload genuinely needs.
  • Pods of a Deployment, DaemonSet or other workload are admitted with the SCCs their ServiceAccount may use; an SCC granted to the user who created the workload does not count.
  • privileged: true in the pod spec does not select the privileged SCC by itself: admission takes the highest-priority SCC with allowPrivilegedContainer: true that the requester or ServiceAccount may use.
  • The pod template sets openshift.io/required-scc to an SCC that does not exist, or that neither the requester nor the ServiceAccount may use in the namespace.

Read-only checks

  • oc get events -n {ns} --field-selector reason=FailedCreate
  • oc describe rs -n {ns} -l <app-label> # FailedCreate message lists every SCC tried
  • oc get ns {ns} -o jsonpath='{{.metadata.annotations.openshift\.io/sa\.scc\.uid-range}}'
  • oc adm policy scc-subject-review -f <manifest.yaml> # [OCP] which SCC would admit it

Pod blocked by Pod Security Admission

DBG-PSA · kubernetes, openshift, rosa-classic, rosa-hcp · rules KN-S002, KN-S003, KN-S006, KN-S008

Likely causes

  • Namespace enforces the baseline/restricted Pod Security Standard and the pod spec violates it (missing seccompProfile, capabilities not dropped, allowPrivilegeEscalation not false, runAsNonRoot).
  • The Deployment, Job or other workload was created with a 'would violate PodSecurity' warning (warn and audit check pod templates), but enforce applies only to Pods, so every pod its controller creates is rejected.
  • [OCP] The pod also has to pass its SCC; SCC admission and Pod Security Admission are independent.

Read-only checks

  • oc get ns {ns} --show-labels # pod-security.kubernetes.io/enforce
  • oc get events -n {ns} --field-selector reason=FailedCreate

Pod Pending: insufficient CPU/memory

DBG-PENDING-RESOURCES · kubernetes, openshift, rosa-classic, rosa-hcp · rules KN-C004

Likely causes

  • Requests exceed the free allocatable capacity on every node.
  • Requests are far larger than needed (copied defaults).
  • Cluster autoscaler / machine autoscaling disabled or at max size.

Read-only checks

  • oc describe pod {pod} -n {ns} # FailedScheduling details per node
  • oc describe nodes | grep -A8 'Allocated resources'
  • oc get machineautoscaler,clusterautoscaler -A # [OCP]
  • rosa list machinepools -c <cluster> # [ROSA] autoscaling min/max

Pod Pending: taints, node selectors or affinity

DBG-PENDING-PLACEMENT · kubernetes, openshift, rosa-classic, rosa-hcp · rules KN-C010, KN-ST003

Likely causes

  • nodeSelector/affinity targets labels no schedulable node has.
  • Nodes are tainted (infra, GPU, control-plane) and the pod has no toleration.
  • Required (DoNotSchedule) topology spread or anti-affinity cannot be satisfied with current nodes.
  • Zonal volume exists in a zone with no eligible node ('volume node affinity conflict').

Read-only checks

  • oc describe pod {pod} -n {ns}
  • oc get nodes -L topology.kubernetes.io/zone,node-role.kubernetes.io/worker
  • oc get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints

PersistentVolumeClaim stuck in Pending

DBG-PVC-PENDING · kubernetes, openshift, rosa-classic, rosa-hcp · rules KN-ST001, KN-ST004, KN-ST005

Likely causes

  • Access mode unsupported by the class: ReadWriteMany on EBS (gp3-csi/gp2-csi) or Ceph RBD filesystem.
  • StorageClass name does not exist or there is no default StorageClass.
  • WaitForFirstConsumer: normal until a pod using the claim is scheduled.
  • CSI driver not installed (e.g. EFS CSI Driver Operator on ROSA) or lacks cloud permissions.

Read-only checks

  • oc describe pvc {pvc} -n {ns} # Events show the provisioner error
  • oc get storageclass
  • oc get csidriver
  • oc get pods -n openshift-cluster-csi-drivers # [OCP]

Volume Multi-Attach error

DBG-MULTIATTACH · kubernetes, openshift, rosa-classic, rosa-hcp · rules KN-ST002

Likely causes

  • A ReadWriteOnce volume is mounted by pods on different nodes: several replicas sharing one claim, or a RollingUpdate surge pod scheduled to another node.
  • The previous node died and the attachment has not been released yet (VolumeAttachment still present).

Read-only checks

  • oc describe pod {pod} -n {ns}
  • oc get volumeattachment | grep <pv-name>
  • oc get pods -n {ns} -o wide # which nodes hold pods using the claim

Volume mount failures (FailedMount / permission denied)

DBG-MOUNT · kubernetes, openshift, rosa-classic, rosa-hcp · rules KN-S007

Likely causes

  • Referenced Secret/ConfigMap volume missing.
  • Filesystem ownership does not match the container UID/GID (fsGroup missing on vanilla Kubernetes; arbitrary UID on OpenShift).
  • readOnlyRootFilesystem: true while the app writes outside its mounted emptyDir paths.
  • NFS/EFS mount blocked: the node cannot reach the NFS server or EFS mount target (a firewall or security group on TCP 2049, no EFS mount target in the node's subnet) or the server's export does not allow the node.

Read-only checks

  • oc describe pod {pod} -n {ns}
  • oc rsh -n {ns} {pod} ls -ln <mount-path> # numeric owner vs `id`

Readiness/liveness probe failures

DBG-PROBE · kubernetes, openshift, rosa-classic, rosa-hcp · rules KN-C001, KN-C002, KN-C003

Likely causes

  • Probe port/path does not match what the app serves (wrong port name, /healthz vs /health).
  • App listens on 127.0.0.1 instead of 0.0.0.0, so the kubelet cannot reach it.
  • timeoutSeconds too low or the health endpoint checks slow dependencies.
  • App needs more startup time (use startupProbe).

Read-only checks

  • oc describe pod {pod} -n {ns} # probe definition and failure message
  • oc rsh -n {ns} {pod} curl -sv localhost:<port><path>
  • oc logs {pod} -n {ns}

Route returns 503 'Application is not available'

DBG-ROUTE-503 · openshift, rosa-classic, rosa-hcp · rules KN-V011, KN-V012, KN-N001, KN-N002

Likely causes

  • The Service behind the Route has no ready endpoints (selector mismatch or pods not ready).
  • Route port.targetPort does not name a Service port.
  • Wrong TLS termination: edge Route to an HTTPS-only backend (use reencrypt/passthrough) or reencrypt to a plain HTTP backend.
  • NetworkPolicy blocks the router: allow namespaceSelector policy-group.network.openshift.io/ingress: "".
  • Route not admitted: host already claimed by another namespace (HostAlreadyClaimed).

Read-only checks

  • oc get route {name} -n {ns} -o yaml # status.ingress[].conditions
  • oc get endpointslices -n {ns} -l kubernetes.io/service-name={svc}
  • oc get pods -n {ns} --show-labels
  • oc get networkpolicy -n {ns}

Service has no endpoints

DBG-NO-ENDPOINTS · kubernetes, openshift, rosa-classic, rosa-hcp · rules KN-V011, KN-V012

Likely causes

  • Service selector does not match pod labels.
  • Pods are not Ready (readiness failing), so they are excluded.
  • targetPort names a port the container does not declare.

Read-only checks

  • oc describe svc {svc} -n {ns}
  • oc get endpointslices -n {ns} -l kubernetes.io/service-name={svc} -o wide
  • oc get pods -n {ns} -l {selector} -o wide

API request forbidden (RBAC)

DBG-RBAC · kubernetes, openshift, rosa-classic, rosa-hcp · rules KN-S015, KN-S016, KN-S017

Likely causes

  • The ServiceAccount/user lacks a Role/ClusterRole granting the verb on that resource and API group.
  • RoleBinding is in a different namespace than the resource.
  • Wrong apiGroup in the Role (e.g. '' vs 'apps').

Read-only checks

  • oc auth can-i {verb} {resource} -n {ns} --as={subject}
  • oc get rolebinding,clusterrolebinding -A -o wide | grep -- '{subject}'

Admission webhook denied or failed

DBG-WEBHOOK · kubernetes, openshift, rosa-classic, rosa-hcp

Likely causes

  • A policy engine (RHACS/StackRox, Gatekeeper, Kyverno) rejected the object - the message names the policy.
  • The webhook service is down/unreachable and failurePolicy is Fail, blocking all matching requests.
  • Kyverno: the API server cannot reach the Kyverno webhook on the worker nodes (TCP 9443 by default). A private GKE cluster does not allow that traffic from the control plane until a firewall rule opens it; on EKS a custom CNI such as Calico, an outdated VPC CNI plug-in, or a node security group without an inbound rule for 9443 from the cluster security group has the same effect (failed calling webhook "validate.kyverno.svc-fail": ... context deadline exceeded).
  • Kyverno: every Kyverno pod is down while policies matching Pods fail closed, so the API server times out on those requests.

Read-only checks

  • oc get validatingwebhookconfigurations,mutatingwebhookconfigurations # age should match its pods
  • oc get validatingwebhookconfiguration <name> -o jsonpath='{{.webhooks[*].failurePolicy}}'
  • kubectl get pods -n kyverno # Kyverno pods must be Running

Request denied by a ValidatingAdmissionPolicy (a CEL validation is false)

DBG-VAP · kubernetes, openshift, rosa-classic, rosa-hcp

Likely causes

  • One of the policy's spec.validations CEL expressions returned false for this object, and the binding in the message has validationActions: [Deny]. 'failed expression: <expr>' quotes the expression itself (the validation has no message or messageExpression); any other text is the policy's message.
  • Every matching (policy, binding, parameter) combination must pass, so a second binding or parameter resource can deny what another allows.

Read-only checks

  • kubectl get validatingadmissionpolicy <policy> -o yaml # spec.validations, failurePolicy, status.typeChecking
  • kubectl get validatingadmissionpolicybinding <binding> -o yaml # validationActions, matchResources, paramRef

RHACS / StackRox admission controller blocked a deployment

DBG-STACKROX-ADMISSION · kubernetes, openshift, rosa-classic, rosa-hcp · rules KN-S001, KN-S012, KN-C004, KN-S003

Likely causes

  • A RHACS policy with deploy-time enforcement matched (e.g. Privileged Container, Latest tag, No resource requests or limits, root user).
  • Admission controller enforcement is enabled for the cluster (secured cluster admissionControl.enforce, the 4.9+ setting replacing enforceOnCreates/enforceOnUpdates).

Read-only checks

  • Read the policy names in the denial message.
  • roxctl deployment check --file=<manifest.yaml> -e <central:443> # same evaluation, offline from apply
  • oc get validatingwebhookconfiguration stackrox -o yaml

Helm: another operation is in progress

DBG-HELM-LOCK · kubernetes, openshift, rosa-classic, rosa-hcp

Likely causes

  • A previous helm install/upgrade was interrupted, leaving the release in a pending-* state.

Read-only checks

  • helm history <release> -n {ns}
  • helm status <release> -n {ns}

Helm: resource exists and is not managed by this release

DBG-HELM-OWNERSHIP · kubernetes, openshift, rosa-classic, rosa-hcp

Likely causes

  • The object was created outside Helm (kubectl apply, operator, other release).

Read-only checks

  • oc get <kind> <name> -n {ns} -o jsonpath='{{.metadata.labels}}{{.metadata.annotations}}'

API kind not found (no matches for kind / removed API)

DBG-NO-MATCHES-KIND · kubernetes, openshift, rosa-classic, rosa-hcp · rules KN-V002, KN-V003, KN-V004, KN-V005

Likely causes

  • The apiVersion was removed in this Kubernetes/OpenShift version (e.g. policy/v1beta1 PDB in 1.25).
  • The CRD is not installed (operator missing) or the kind belongs to another platform (Route on vanilla Kubernetes).
  • Wrong group for the kind (Route is route.openshift.io/v1, not apps.openshift.io/v1).

Read-only checks

  • oc api-resources | grep -i <kind>
  • oc version # server Kubernetes version
  • kube-noob audit -f <manifest.yaml> --platform <platform> --version <ocp-or-k8s-version>

Pods evicted (node pressure)

DBG-EVICTED · kubernetes, openshift, rosa-classic, rosa-hcp · rules KN-C004, KN-C005

Likely causes

  • Node ran out of memory or disk; BestEffort/Burstable pods exceeding requests are evicted first.
  • Container writes logs/temp files to the container filesystem (ephemeral-storage) without limits.

Read-only checks

  • oc get pods -n {ns} --field-selector status.phase=Failed
  • oc describe node <node> | grep -A5 Conditions

DNS resolution failures inside pods

DBG-DNS · kubernetes, openshift, rosa-classic, rosa-hcp

Likely causes

  • Egress NetworkPolicy blocks DNS (OpenShift DNS listens on 5353 in openshift-dns; CoreDNS on 53 in kube-system).
  • Wrong service name/namespace (use <svc>.<ns>.svc.cluster.local).
  • Upstream resolver/VPC DNS issue for external names (ROSA private clusters: VPC DNS hostnames/resolution must be enabled).
  • CoreDNS itself: its pods are not Running, the kube-dns Service has no endpoints, or the ClusterRole system:coredns lacks list/watch on Services and EndpointSlices (SERVFAIL in its logs).

Read-only checks

  • kubectl exec -ti {pod} -n {ns} -- cat /etc/resolv.conf # nameserver = the cluster DNS Service IP
  • oc rsh -n {ns} {pod} getent hosts kubernetes.default.svc
  • kubectl get pods -n kube-system -l k8s-app=kube-dns # [K8S] CoreDNS
  • kubectl logs -n kube-system -l k8s-app=kube-dns # [K8S]
  • kubectl get endpointslice -l kubernetes.io/service-name=kube-dns -n kube-system # [K8S]
  • oc get networkpolicy -n {ns} -o yaml | grep -B3 -A10 egress

Traffic blocked between pods / to the internet

DBG-NETPOL · kubernetes, openshift, rosa-classic, rosa-hcp · rules KN-N006, KN-V015, KN-N001

Likely causes

  • A default-deny NetworkPolicy without an allow rule for this source/port.
  • [OCP] EgressFirewall denies the destination (rules are first-match; a leading Deny 0.0.0.0/0 blocks everything after it).
  • Cloud security groups / firewall outside the cluster.

Read-only checks

  • oc get networkpolicy -n {ns}
  • oc get egressfirewall -n {ns} -o yaml # [OCP]
  • oc rsh -n {ns} {pod} curl -sv --max-time 5 <target>

oc / kubectl cannot verify the API server's certificate

DBG-X509-CLIENT · kubernetes, openshift, rosa-classic, rosa-hcp

Likely causes

  • The kubeconfig does not trust the CA that signed the API server certificate (new cluster, rotated certificate, or a corporate proxy that re-signs TLS).
  • The kubeconfig points at the wrong server, or the machine clock is skewed.
  • After kubeadm reset and kubeadm init the cluster has a new CA, but ~/.kube/config still holds the old cluster's certificates (crypto/rsa verification error naming the CA "kubernetes").

Read-only checks

  • oc config view --minify -o jsonpath='{{.clusters[0].cluster.server}}' # which API server you call
  • openssl s_client -connect <api-host>:6443 -servername <api-host> </dev/null | openssl x509 -noout -issuer -subject -dates
  • date -u # clock skew breaks certificate validity

TLS / certificate errors

DBG-X509 · kubernetes, openshift, rosa-classic, rosa-hcp

Likely causes

  • Expired certificate (check notAfter), clock skew, or the client does not trust the issuing CA.
  • Hostname mismatch (SAN does not include the host being called).

Read-only checks

  • oc get events -n {ns} --sort-by=.lastTimestamp # which component reports the x509 error
  • oc get route -n {ns} -o wide # TLS termination per Route
  • openssl s_client -connect <host>:443 -servername <host> </dev/null | openssl x509 -noout -dates -subject -ext subjectAltName

exec format error (wrong CPU architecture)

DBG-EXEC-FORMAT · kubernetes, openshift, rosa-classic, rosa-hcp

Likely causes

  • The image was built for another architecture (arm64 image on amd64 nodes or vice versa), or the entrypoint script lacks a shebang.

Read-only checks

  • skopeo inspect --raw docker://<image> | jq '.manifests[].platform'
  • oc get nodes -L kubernetes.io/arch

Container command not found in the image (executable file not found)

DBG-ENTRYPOINT-NOT-FOUND · kubernetes, openshift, rosa-classic, rosa-hcp

Likely causes

  • The container's command (the pod's command, or the image's ENTRYPOINT and CMD) names a program that is not in the image or not on its PATH: runc looks it up when it creates the container.
  • A multi-stage build left the program in an earlier stage (only what COPY --from copies reaches the final image).
  • kubectl exec into an image without a shell (distroless and other minimal images): `exec: "sh"` or `"bash"`: executable file not found. The container is fine; it has no shell to start.

Read-only checks

  • kubectl get pod {pod} -n {ns} -o jsonpath='{{.spec.containers[*].command}} {{.spec.containers[*].args}}'
  • kubectl describe pod {pod} -n {ns} # the Events carry the runtime's error with the program's name
  • docker image inspect <image> --format '{{{{.Config.Entrypoint}}}} {{{{.Config.Cmd}}}}'

Rejected by ResourceQuota / LimitRange

DBG-QUOTA · kubernetes, openshift, rosa-classic, rosa-hcp · rules KN-C004, KN-C005

Likely causes

  • Namespace quota exhausted, or the quota covers limits/requests and the pod does not set them.

Read-only checks

  • oc describe quota -n {ns}
  • oc describe limitrange -n {ns}

Node drain / upgrade blocked by PodDisruptionBudget

DBG-PDB-DRAIN · kubernetes, openshift, rosa-classic, rosa-hcp · rules KN-C009

Likely causes

  • PDB allows zero disruptions (minAvailable == replicas, maxUnavailable: 0) or the workload is unhealthy.

Read-only checks

  • oc get pdb -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,ALLOWED:.status.disruptionsAllowed

HorizontalPodAutoscaler shows <unknown> / does not scale

DBG-HPA · kubernetes, openshift, rosa-classic, rosa-hcp · rules KN-C012

Likely causes

  • Target containers lack CPU requests, or the metrics API (metrics-server / OpenShift monitoring) is unavailable.

Read-only checks

  • oc describe hpa {name} -n {ns}
  • oc get apiservice v1beta1.metrics.k8s.io

Job failed (BackoffLimitExceeded / DeadlineExceeded)

DBG-JOB · kubernetes, openshift, rosa-classic, rosa-hcp

Likely causes

  • The job's pod exits non-zero repeatedly or exceeds activeDeadlineSeconds.

etcd is slow or unstable (leader changes, slow disk, no leader, database space)

DBG-ETCD · kubernetes, openshift

Likely causes

  • Slow disk under etcd: every write is persisted before it is acknowledged, so disk latency is part of leader liveness. A WAL fsync p99 above 10 ms or a backend commit p99 above 25 ms makes the leader miss heartbeats, members hold elections, and the API server times out.
  • CPU starvation on the control-plane nodes, the second most common cause of missed heartbeats.
  • Slow or lossy network between control-plane nodes (high round-trip time between zones).
  • The database reached its space quota: etcd raises a NOSPACE alarm and accepts only reads and deletes (`mvcc: database space exceeded`) until it is compacted, defragmented and the alarm is cleared.
  • A member is down or its node is NotReady; with too few members the cluster loses quorum and has no leader.
  • A product bug that adds control-plane I/O: check the reported issues listed for your version.

Read-only checks

  • oc get co etcd kube-apiserver # [OCP] Degraded or Progressing, and since when
  • oc describe co etcd # [OCP] the operator's messages name the failing member or check
  • oc get pods -n openshift-etcd -l k8s-app=etcd -o wide # [OCP] one per control-plane node, restarts
  • kubectl get pods -n kube-system -l component=etcd -o wide # [K8S] kubeadm runs etcd as a static pod
  • oc get nodes -l node-role.kubernetes.io/master # [OCP] control-plane nodes Ready?
  • kubectl get nodes -l node-role.kubernetes.io/control-plane # [K8S] control-plane nodes Ready?

RHACS: emergency bypass of admission enforcement (admission.stackrox.io/break-glass)

DBG-RHACS-BREAK-GLASS · kubernetes, openshift, rosa-classic, rosa-hcp

Likely causes

  • An urgent deployment is blocked by an enforced RHACS policy. The admission controller lets a Deployment through when it carries the annotation admission.stackrox.io/break-glass, provided the secured cluster allows bypass.
  • Each bypass is recorded as a violation of the 'Emergency Deployment Annotation' policy (high severity; the docs call it 'StackRox Emergency Deployment Annotation'), with the deployment details.
  • Bypass is turned off on the cluster, so the annotation does not help: Operator admissionControl.bypass: Disabled, Helm admissionControl.dynamic.disableBypass: true, a bundle generated with roxctl sensor generate --admission-controller-disable-bypass, or the portal setting 'Admission controller bypass annotation' not Enabled.

Read-only checks

  • oc get deployment <name> -n {ns} -o jsonpath='{{.metadata.annotations}}' # annotation on the Deployment

RHACS admission webhook error or timeout (failure policy Fail rejects the request)

DBG-RHACS-WEBHOOK-FAILURE-POLICY · kubernetes, openshift, rosa-classic, rosa-hcp

Likely causes

  • The RHACS validating webhook (policyeval.stackrox.io, or k8sevents.stackrox.io for exec and port-forward) hit an error or a timeout, and the cluster's admission controller failure policy is Fail (fail closed), so the API server rejects the request. The default, Ignore (fail open), admits it.
  • Admission enforcement adds latency to every evaluated API call; clients with short default API timeouts (the docs name fabric8) can give up first.
  • The webhook timeout cannot be raised: admissionControl.timeoutSeconds and --admission-controller-timeout are deprecated and ignored (RHACS uses a preset timeout).

Read-only checks

  • oc get validatingwebhookconfiguration stackrox -o jsonpath='{{.webhooks[*].failurePolicy}}' # Fail = fail closed, Ignore = fail open
  • oc get deployment admission-control -n stackrox # the service the webhooks call
  • Portal: Platform Configuration -> Clusters -> 'Admission controller failure policy'
